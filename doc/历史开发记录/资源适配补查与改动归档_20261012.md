## CPU 与可并行工作的核对

复杂样例保存约 99 秒，其中保存观测 CPU 约 98 秒。诊断阶段显示覆盖复算、原目标建账及几何验证为主要开销；嵌套时间不相加，也不能将墙钟/CPU 差值当作 I/O 等待。当前进程允许 18 个逻辑 CPU，由 Windows `GetProcessAffinityMask` 实际查询；可用内存约 0.3 GiB 的一次查询下，候选策略仍选择一个摘要工作线程，不因 CPU 数量高或物理内存总量增加而扩并行。

准备并行的是相互独立的文件摘要，几何证明遍历、候选顺序和预算计数继续串行。候选策略需要至少 4 个文件、合计至少 16 MiB、进程可用逻辑 CPU 至少 4，且当前可用内存扣除系统/界面预留量后仍至少 512 MiB；最多两个工作线程。未知 CPU/内存、少量文件和低余量保守回退到一个。线程不拿调用方的预算/取消回调，调用方线程持续检查；异常或取消会停止并等待工作线程，只有完整结果按原输入顺序返回。

## 已复现的两个内存细节

现有 Windows 内存查询每次声明新的 ctypes Structure/POINTER，20 次查询后 ctypes 类型缓存增加 20 项，GC 后仍保留。暂存修复把类型移到模块范围，API 绑定使用最多一项的惰性缓存，每次仍查询当前系统状态；40 次查询没有继续增加类型缓存。同一资源观测下的配置决策和保守失败回退保持，3 项专项通过。该结果说明缓存增长被阻断，不将类型项数换算为完整应用的 RAM 节省。

现有诊断对已被上层处理的预算中断保留异常 traceback，直到整项任务结束，可能暂时保留计算对象。弱引用用例复现了一个 1 MiB 测试对象在父阶段成功后仍被保留。暂存修复在成功的父阶段释放已处理异常的引用，下一计算开始前对象即可回收；真正向外传播的显式异常链仍保留最内层失败阶段和原异常身份，2 项专项通过。该结果不等于实机应用已获得 1 MiB 或更多的进程内存降幅。
