# 工程清单写入与保存中断保护（2026-10-11）

本轮继续处理上一轮遗留的便携工程保存超时。生产修改限于共享 JSON 写入器与工程保存／回读入口，改善清单写入的临时内存、取消与大小检查，并补充可定位具体阶段的日志。未扩展 P5 变宽补线或 P6 跨会话继承。

## 实现

共享 `io_utils.write_json` 增加可选 `check` 和 `max_bytes`。启用任意一项后，以 JSON 编码迭代器输出到独立临时文件，按原 UTF-8 和平台换行累计字节；每批输出小于 128 KiB，每批及每 1,024 个编码片段检查任务回调，最终替换前再次检查。超限、取消、超时或写入失败不替换原文件，临时清理失败不掩盖原异常。缺省调用仍使用原写入实现。

便携保存和回读的 `project.json` 使用原 100 MiB 上限，在下一批将要越界时拒绝，原保存后的大小检查继续保留。保存拒绝非有限数；回读保留原解析语义，后续数值校验仍完整执行。临时 `candidate_path.json` 同样分段写入并检查原任务回调，沿用原路线读取限额。JSON 字段、顺序、浮点值、转义和换行字节保持。

新增 `portable.manifest`、`portable.validation_manifest` 与 `portable.archive` 阶段，分别记录工程清单、临时验证清单及 ZIP 压缩落盘。原 120 秒操作限额、完整目标与覆盖复算、原生／便携发布顺序、保存凭据及失败后的页面状态保持。单个字符串编码和操作系统调用仍是合作式边界，不能保证硬实时中断。

## 故障定位与环境

开工时源码与上轮封存的 573 个文件一致；278 份原资产、13,941 份此前证据及环境清单均核对。原始未修改基线在工程打开阶段用时 129.388 秒，触发原 120 秒预算，保存尚未开始。该失败及当时脚本保留于 `baseline_save_run`。

随后只读观察到本机总内存 16,513,519,616 字节（约 15.38 GiB），可用内存分别约 14 MiB、115 MiB；系统提交量约 49.56 GB，换入页数约 12,214／秒。各数值来自不同时刻的采样，不能当作同一瞬间的完整快照，也不能单凭它们断言上轮超时的底层原因。

本轮对照在相同当前流程中切换原整块清单写入与新分段写入，几何、验证和 ZIP 打包流程相同。旧模式第一次保存 93.5068 秒，清单写入为 0.1204 秒；第二次清单输出阶段耗时 47.3536 秒，46 个调用栈采样停留在 `Path.write_text` 的文本输出调用，整个后台操作在 135.1179 秒后以原预算错误结束。验收等待另在 135.6677 秒报超限，两处结果分别记录。第二次保存采样区间可用内存约 9.21–328.13 MiB。原生包已成功发布，便携包未完成；第三次未执行，全部失败记录保留。

这些证据将本轮可复现的长停顿缩小到整块清单输出调用，内存压力是同时观察到的环境因素；底层文本编码、换页或文件系统等待的具体贡献仍未分离，不把它们写成已经确定的设备故障原因。

旧方式只有一次成功和一次失败，没有完整三次基线，不计算前后完整保存提速百分比。本轮确定的改善是清单临时分配量降低、预算／取消检查细化以及失败可定位；不能由本次结果推断所有工程、所有内存状态下的总保存耗时都会下降。
