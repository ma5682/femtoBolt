## 超时定位：测试等待方式，而非几何优化

最初采样栈停留在 `nearest_boundary_distances → edge_checks → VerifiedSurfaceGraph`，这只能说明采样时执行位置，不能证明几何算法本身导致 60 秒超时。进一步实验证实：

| 对照 | 结果 | 证据 |
|---|---|---|
| 同一默认合成选区，同步调用生成器，带 cProfile | 约 10.547 秒完成 | `profile_planning.py`、`before.prof`、`before_profile.txt`、`before_plan.json` |
| 后台生成，主线程循环 `QTest.qWait(20)`，60 秒截止 | 60.016 秒仍 busy；随后按正常取消路径结束 | `profile_worker.py qwait`、`worker_qwait.log`、`worker_qwait_profile.txt` |
| 同一后台生成，主线程 `QEventLoop.exec()`，同样 60 秒截止 | 生成约 11.125 秒；包括验证和结果投递约 12.266 秒，busy=False，无错误 | `profile_worker.py eventloop`、`worker_eventloop.log`、`worker_eventloop_profile.txt` |
| 不含规划的一秒线程调度对照，后台反复做相同 NumPy 范数计算 | qWait：1.015 秒 / 1,653 次；Qt 事件循环：1.016 秒 / 953,454 次 | `wait_scheduling.py`、`wait_scheduling.json` |

以上是本机的定性调度对照，早期诊断进程存在重叠，不作为产品性能基准。独立的一秒对照和随后串行项目回归共同验证处理方向。qWait profile 中约 54.4 秒记在等待函数；跨线程 C 扩展的 cProfile 归账不应当成各几何函数的独占 CPU 时间。

当前 PySide6/CPython 组合下，循环 qWait 会严重挤占 Python 后台任务运行机会。修复 `QtPlanningTests.wait_task`：用正常嵌套 Qt 事件循环等待 `runner.finished`，单次 QTimer 保持 **60,000 ms** 截止，finally 停止计时器并断开信号。仍断言任务已结束且无错误；后续真实规划、保存、回放、取消与参数测试保持原行为。

**生产 Python 无修改**：没有加入距离缓存、图搜索捷径、cleanup workaround，也没有改变候选、预算、浮点容差、质量门禁或路线结果。
