# 硬件接口预留契约

> 2026-10-21 后续实现见 [模拟联调与坐标准备契约](模拟联调与坐标准备契约_20261021.md)。本文“尚无模拟适配器/暂停意图/UI/事件存储”的描述为原预留阶段状态，已由后续契约取代；真实厂家控制仍未实现。原五个意图和校验语义继续兼容。

本文供软件开发者和后续设备联调人员使用。目标是在设备尚未到位时，明确软件要发送什么意图、接收什么反馈，以及哪些信息必须等待厂家协议。本文对应 2026-10-20 的代码状态。

当前新增的是进程内 Python 数据契约及校验函数，不是设备通信协议。它不会打开设备、发送运动或治疗指令、更新历史数据库，也不会把测试反馈安装为真实采集结果。

## 当前已实现的边界

| 部分 | 当前实际能力 | 可复用内容 | 尚未提供 |
| --- | --- | --- | --- |
| 相机 SDK | `OrbbecAlignedCamera.start/read/stop`；读取对齐 RGB-D、标定、设备元数据及读取诊断 | 单独相机封装、原始帧字段、真实来源记录 | 不据此推断机械臂位姿或其他设备时钟同步 |
| 相机线程 | Qt `CameraHost` 与 `CameraWorker` 通过命令和事件队列协作 | 单个 SDK 所有者、会话关联、停止及迟到事件处理模式 | 通用设备总线、厂家协议适配器 |
| 补扫任务交换 | `scan_exchange` 校验批次、会话、模型、标定、RGB-D 时间戳和内部采集记录 | 请求与观测分离；内部采集门控拥有最终融合接纳权 | 机械臂移动指令、自动补扫完成认证 |
| 机械臂、底座、治疗头 | 无真实驱动、无通信配置、无设备协议 | 本文列出的数据边界和待确认项 | 连接、回零、运动、停止确认、治疗输出等真实操作 |
| 新接口预留 | `interface_contract.py` 的不可变数据类和校验函数 | 身份、来源、连接代次、请求关联、能力及反馈阶段 | transport、SDK 调用、UI 接入、持久化事件流、实时控制循环 |

相机实现见 [orbbec_rgbd.py](../../femto/hardware/orbbec_rgbd.py)、[camera_worker.py](../../femto/app/camera_worker.py)。现有交换契约见 [scan_exchange.py](../../femto/capture/scan_exchange.py)、[capture_exchange.py](../../femto/capture/capture_exchange.py)。

## 现有相机与补扫数据不能被省略

`AlignedFrame` 已保留彩色、深度、帧序号、彩色与深度的设备/系统时间戳及可用帧元数据。深度数组名为 `depth_mm`；重建和补扫观测的世界坐标以米表示。不能在适配器里只改单位标签而不转换数值。

`scan_exchange` 当前使用以下已实现的 schema：

- `femto-acquisition-task-batch-v1`：任务批次。
- `femto-acquisition-observation-v1`：提供者返回的观测。
- `femto-acquisition-verification-v1`：内部采集门控核验结果。

观测通过封装校验后，`accepted_for_fusion` 仍为 `False`。只有与内部记录的会话、参考帧、标定及时间戳相符，并满足原始写入收据、跟踪、质量和连续性条件，核验结果才可能接纳该帧。

当前观测格式限定 `world_rdf`、`metre`、`T_W0_Ct`；RGB 与 depth 时间戳差不得超过当前代码的 5000 微秒阈值。这个阈值是已有相机采集规则，不是未来机械臂、底座和治疗头的同步精度承诺。

`record_manual_observation` 在原始写入和内部接纳决定之后记录人工补扫交换。任务批次保持请求时的模型绑定；接纳一帧不表示该批所有任务已经解决。`target_improvement` 仍需下一阶段对同一目标进行比较。

## 新增的纯数据接口

实现位于 [interface_contract.py](../../femto/hardware/interface_contract.py)。以下名称是当前 Python API 的实际字段；尚未定义网络包、串口报文或厂家寄存器。

| 数据类 | 字段 | 含义 |
| --- | --- | --- |
| `DeviceBinding` | `device_id`、`kind`、`connection_epoch`、`source` | 设备身份、设备类别、当前连接代次及数据来源 |
| `Capabilities` | `binding`、`protocol_id`、`supported_intents` | 与连接绑定的协议标识和能力声明；默认协议未知、能力为空 |
| `DeviceRequest` | `request_id`、`binding`、`intent`、`related_request_id` | 一次领域意图；取消必须引用被取消请求，且不能引用自身 |
| `DeviceFeedback` | `request_id`、`binding`、`intent`、`sequence`、`phase`、`readiness`、`motion_stopped`、`error_code` | 与请求关联的反馈；未知准备状态保持 `UNKNOWN`，未知停止状态保持 `None` |

设备类别是 `camera`、`arm`、`base`、`treatment_head`。数据来源是 `real`、`replay`、`simulation`；来源在绑定中显式保留。

`connection_epoch` 由未来的设备所有者维护，每次重新建立连接时使用新的代次。`sequence` 由适配层按该请求的反馈次序提供，不能直接假设厂家计数器具有同样含义。二者均不接受布尔值冒充整数。

`validate_request` 校验数据结构和能力适配条件。`validate_feedback` 要求设备身份、类别、连接代次、来源、请求 ID 和意图全部匹配；传入 `last_sequence` 时，还拒绝重复或逆序反馈。两个函数都只返回校验后的数据，不改变设备或采集状态。

`real` 是来源声明，单靠这个字符串不能认证真实设备。后续适配器必须从其持有的真实连接构造绑定，不能把外部输入任意改成 `real`。

## 当前允许表达的意图

| 意图 | 本轮含义 | 校验要求 |
| --- | --- | --- |
| `query_status` | 查询设备报告的状态 | 可以在能力未知时构造；没有发送路径 |
| `query_capabilities` | 查询协议和能力声明 | 可以在能力未知时构造；没有发送路径 |
| `prepare` | 表达准备请求，具体准备动作待协议定义 | 必须有非空 `protocol_id`，且能力明确包含该意图 |
| `cancel_request` | 请求取消指定请求 | 同上，且必须提供 `related_request_id` |
| `request_stop` | 表达停止请求 | 必须有协议和对应能力；不等价于急停或已停止 |

接口没有关节数组、运动轨迹、速度、加速度、治疗功率或治疗时长载荷。即使声明了能力并通过校验，本轮也不会执行意图。

厂家协议到位后，新增运动或治疗参数须使用单独的有版本格式。不能把现有规划点直接塞入 `prepare`，也不能通过任意字典绕过参数、单位和坐标系核验。

## 接收、完成和物理状态分别记录

`FeedbackPhase` 包含 `received`、`completed`、`failed`、`cancelled`。

- `received` 表示提供者报告收到请求，`request_completed` 为 `False`。
- `completed` 表示提供者报告该请求完成，`request_completed` 为 `True`；它不自动改变 `readiness` 或 `motion_stopped`。
- `failed` 和 `cancelled` 不能当作完成。
- `Readiness.UNKNOWN` 不等价于已就绪或安全；未知停止状态不能默认成 `True`。

一次 `request_stop` 收到 `completed`，也不能由软件推导出所有轴已经静止。未来需要厂家定义的反馈来源、停止条件、时效和独立状态核对。

软件请求停止不能替代设备自带的急停、硬件联锁或厂家定义的安全状态。当前代码没有实现这些硬件机制。

## 来源隔离与现有采集门控

回放和模拟数据可以经过纯数据校验，但其来源始终保持 `replay` 或 `simulation`。这类反馈与真实请求绑定不匹配时会被拒绝。

新数据类没有 `accepted_for_fusion` 或 `execution_ready` 字段，也没有安装模型、写入真实历史记录或调用 `scan_exchange.verification` 的入口。因此，模拟的 `completed` 仅用于测试软件分支。

未来接入真实相机提供者时，原始 RGB-D、标定、时间戳、位姿及写入收据仍走现有采集门控。新接口的校验结果不能替代原始证据核验。

## 厂家协议必须补齐的信息

| 设备或主题 | 需要取得的信息 | 当前处理 |
| --- | --- | --- |
| 机械臂 | 厂家型号、SDK/协议版本、轴定义、回零要求、位置/速度单位、目标与实际反馈、限位、故障、停止与取消语义 | 不假定轴数、角度单位或运动方式 |
| 底座 | 轴或运动自由度、定位来源、坐标基准、速度单位、限位、抱闸/停车反馈、机械臂与底座连接关系 | 不把底座视为固定或已知原点 |
| 治疗头 | 厂家支持的准备/启用/停止流程、参数名称和单位、实际输出反馈、接触/温度等可用传感器、故障与联锁信息 | 不声明治疗能力，不填默认治疗参数 |
| 相机安装 | 固定相机或随动相机、实际标定文件、外参方向、标定版本与有效范围 | 不补单位外参；位姿缺失保持未知 |
| 时间同步 | 每类时间戳的时钟域、单位、回绕方式、同步机制、反馈周期、允许延迟和丢包处理 | 不把不同设备时间戳直接相减 |
| 请求生命周期 | 接收与完成确认、请求序号、重复请求、断线重连、超时和取消后的实际状态 | 不自行设定设备控制周期或自动重试运动 |
| 状态与故障 | 状态机、故障码、故障清除条件、停止反馈和心跳失效后的设备行为 | 未知保持未知；软件不自动推断安全状态 |

若采用 eye-in-hand，项目既有约束要求使用同步位姿与标定关系 `T_BC = T_BF · T_FC`。这只是变换关系，不能据此生成未经测量的 `T_BF` 或 `T_FC`。基座、末端、相机、目标模型的坐标含义须由设备与标定资料共同确认。

## 软件测试范围

新增 [test_hardware_interface_contract.py](../../tests/test_hardware_interface_contract.py) 的 8 项纯数据测试已通过，覆盖：

- 能力未知时，仅允许查询类意图。
- 准备、取消和请求停止需要明确协议与能力。
- 收到请求不等于完成，完成也不自动证明准备好或已停止。
- 设备、连接代次、来源、请求 ID、意图及反馈序号错配被拒绝。
- 回放和模拟完成不能用于真实连接。
- 取消关联、不可变记录以及含糊类型被拒绝。

本轮未运行相机，也没有执行机械臂、底座或治疗头联调。已有 `test_scan_exchange`、`test_capture_exchange`、`test_local_session_provenance` 和 `test_qt_capture` 是后续接入时应保留的回归依据；本轮只读核对了这些测试和调用链，未把它们重报为本轮硬件测试。

下一步取得设备协议后，应先编写协议字段映射和离线报文测试，再增加独立适配器。测试报文、回放与真实连接必须分别创建绑定，不能共用完成凭据。

## 数据管理现状复核

单机 SQLite 索引、名称/版本搜索、采集隐藏与恢复、首次任务绑定、元数据发布与失败恢复已经有前一阶段的实现和验收证据。模型、原始图像及方案包继续由原文件和核验机制负责，SQLite 不是设备控制循环。

本次复核了 `asset_storage`、`history_store`、`local_history`、`catalog`、`region_library`、`task_context` 和 `qt_history` 共 7 个源码文件，其 SHA256 均与既有 `completion_audit.json` 的验收快照一致。读取的真实数据验证报告记录 30 条采集、1 条方案和 510 个保护文件核对通过。本次没有重跑重建/规划基准，也没有把旧报告冒充新一轮原始文件摘要检查。

现有证据见 [实施验收记录](../历史开发记录/单机数据架构与性能实施进度_20261020.md)、[SQLite 操作说明](../使用说明/SQLite历史记录与备份.md)、[数据生命周期设计](单机数据访问与文件生命周期设计_20261020.md)。

这些证据不包含多设备服务、完整资产联合备份、自动临时文件清理或硬件执行事件留存。未来设备命令与反馈的存储策略需另行定义；不能把全部高频数据写 SQLite 当作实时控制，也不能因采用内存处理而删除原始证据。
