# 保存后台化：先查看路线，可编辑工程继续写入（2026-11-11）

后续状态：本记录中的 14 项既有失败已在同日后续任务中复现并修复，见[既有测试问题修复](../历史开发记录/既有测试问题修复_20261111.md)。下列全量日志和测试数字保留为本阶段历史结果。

范围：仅 Qt 工作台 `femto/app/` 的保存交互与关窗流程。保存内容、核验次数、预算、算法版本、文件格式和诊断阶段名均未改变。仅源码，未重新打包 EXE，未提交。

## 背景

`PlanningPage.save_plan` 的后台任务按顺序执行：选区检查 → 原生三维路线包（`surface_workspace.export`）→ 可编辑工程（`region_project.save_project`，`planning.region.zip`）。改动前页面要等整条任务结束才解除“处理中”。既有诊断记录中两次实际规模保存的可编辑工程阶段为 3.4–4.6 秒，约占保存等待的三成。

可编辑工程写入失败原本就按“三维路线已保存、可编辑工程未完成”单独报告，两段在语义上已经可以分开提示。

## 改动

1. 工作线程在原生路线包发布后，向界面线程发出一次带任务令牌的通知，然后在**同一线程、同一 `SaveValidationSession` 和同一 `geometry_operation()` 作用域**内继续写可编辑工程。会话的线程绑定、状态机、每次输入重哈希和一次性消费都没有变化；没有新增线程，也没有跨请求复用任何核验结果。
2. 页面收到通知后进入“收尾”状态（`PlanningPage.finishing_save`，值为已发布的路线目录）：
   - 状态栏显示“三维路线已保存，正在写入可编辑工程…”，后续进度前缀“三维路线已保存 · ”。
   - 在第一个阶段切换参考图和三维视图时，保留保存进度提示，避免被涂抹操作提示覆盖。
   - 只放开只读查看：路线显示、播放、本页三个阶段之间切换（标签、上一步、流程条的本页步骤、路线页的“下一步：核对并保存”）。
   - `usable()` 保持原语义（任务运行期间为假），所有会启动任务的入口仍被它和 `busy` 挡住。新增的 `viewable()` 只用于显示和页内导航。
   - 参数、选区、备注、核对勾选、保存、另存、报告、覆盖核验、打开方案等输入保持禁用。
3. `archive`、`dirty`、`project_id`、`revision_id`、保存警告、草稿清理、`saved` 信号和“查看已保存结果”仍然只在可编辑工程写完后的原完成回调 `_saved()` 中提交。收尾期间页面不显示“规划方案已保存”。
4. 离开规划页的入口全部保持阻断：`can_leave()` 返回假并说明原因；`WorkflowNavigation` 对离开页面的步骤返回“三维路线已保存，可编辑工程正在写入；写完后才能切换。”；`open_planning`、`open_review`、`new_task`、`show_capture`、`show_devices`、`rescan_region` 的既有 `busy` / `can_leave()` 判断未改。
5. 关窗：收尾期间请求关闭不再询问“是否结束任务”，也不取消写入。窗口禁用并提示“写完后自动关闭”，由既有 250 ms 重试计时器在写完后关闭。若可编辑工程写入失败，窗口恢复可用并弹出“可编辑工程未保存”，方案保留可重存。其他任务运行时的关窗流程不变。
6. 取消：收尾期间“取消任务”仍可用，提示说明会停止写入、已写出的路线文件保留、方案不记为已保存。点击后收尾状态立即结束，页面回到普通“正在取消”的全锁定状态，结束提示沿用原有“任务已取消”。
7. `tools/profile_qt_save.py` 增加 `route_release_seconds`（调用 `save_plan()` 到界面线程收到路线发布通知）和 `complete_seconds`，原有阶段、检查和通过条件不变；旧后端不产生前者。

通知只在三个条件同时成立时生效：令牌属于当前保存任务、任务仍在运行、尚未请求取消。完成后到达的旧通知、其他任务期间的通知和取消后的通知都被忽略，并有测试覆盖。

## 没有改变的内容

- 原生路线包与可编辑工程的内容、顺序、核验、120 秒操作预算和 `GeometryBudget` 取消检查。
- 进度文本 `1/4`–`4/4`、失败文本“三维路线已保存到 …；可编辑工程保存未完成：…”、诊断阶段 `save.selection_assessment` / `save.route_and_native` / `save.portable_project`。
- 另存（`save_as`）仍是单段任务。
- 结果安装前的输入修订比对（`TaskRunner` 的 `install_allowed`）。收尾期间所有输入锁定，修订不会变化。

| 代号 | 方案 | 路线 |
|---|---|---|
| single_20261109 | `outputs/planning_models/5d2a3b19…/trajectory_7f1d8cfaf7dc/planning.region.zip` | 2 段 1258 点 15 行 |
| capture_20261106 | `outputs/planning_models/6269d8b7…/trajectory_fc0568c53797/planning.region.zip` | 2 段 2044 点 18 行 |

方法：冻结改动前后两份 `femto/*.py` 归档（仅三个改动文件不同，411 个模块），用同一份 `tools/profile_qt_save.py` 经 `tools/run_archived_backend.py` 在新进程中调用真实 `PlanningPage.save_plan`，每份输入按 旧/新/新/旧 顺序各跑一轮，离屏 Qt。每次保存后原生与便携结果都完整独立回读并核对路线和证据，8 次全部通过，归档与工具文件摘要前后一致。

“等待”的定义：旧实现取完整保存时间（页面只在完成回调后解除）；新实现取路线发布通知触发界面线程状态信号的时间。该时间戳早于随后调用的 `refresh()`，不等于控件已完成刷新或屏幕已显示的时刻。

| 输入 | 等待（旧 → 新，秒，两次均值） | 减少 | 完整保存（旧 → 新，秒） |
|---|---|---|---|
| single_20261109 | 8.765 → 5.794 | 2.970 秒（33.9%） | 8.765 → 8.812 |
| capture_20261106 | 10.643 → 6.809 | 3.835 秒（36.0%） | 10.643 → 10.418 |

逐次数值：single 旧 8.862 / 8.667，新 5.829 / 5.760；capture 旧 10.350 / 10.937，新 6.819 / 6.798。可编辑工程阶段本身为 2.73–2.89 秒和 3.33–3.60 秒，未变快。

说明：

- 总保存时间没有缩短，变化在同机波动范围内。减少的是界面收到“三维路线已保存”通知之前的等待；“规划方案已保存”和查看保存结果仍要等到可编辑工程写完。
- 每份输入每个版本只有两次，样本小；测量时本机可用内存约 0.5 GiB、其他程序占用 CPU 约 18–20%。数值只说明这两份输入在当时条件下的结果，不外推到多帧、带覆盖证据的方案或其他机器。
- 通知到达后界面线程的一次刷新在 single 输入上另测中位数约 0.08 秒（`refresh_cost_p0/result.json`）。这次 `refresh()` 发生在计时信号之后，未包含在表中的新版本等待数值内。原稿写成“已包含”，接续核查按调用顺序纠正。
- 离屏 Qt 不含真实屏幕渲染和人工操作时间。

## 验证

新增 `tests/test_qt_save_background.py` 8 项，全部使用真实保存流程，只在可编辑工程入口处暂停工作线程：

- 路线发布后页面放开查看，同一工作线程继续写工程；提交状态只在完成后改变。
- 收尾期间输入和各任务入口保持锁定，重复调用保存、生成、报告、另存、覆盖核验都不会启动任务。
- 页内阶段切换可用；会返回采集页的“上一步”保持禁用（含区域优先模型）。
- 工程写入失败：方案保留、未记为已保存、可重新保存成功。
- 收尾期间取消：立即回到全锁定，结束后为普通取消，未生成工程文件。
- 旧令牌、空令牌、外来令牌和取消后的通知都不会放开页面。
- 主窗口：离开页面的全部入口阻断，本页步骤可用；关窗等待写完后自动关闭；写入失败时窗口保持打开并提示。

另有 Windows 原生 Qt/VTK 隐藏窗口检查，使用独立工作目录和既有实采方案，不连接相机。原会话的脚本直接重存“已保存”的方案，只验证了部分控件状态；2026-11-11 接续检查补充了与 `load_source(new_version=True)` 相同的待保存状态，从可用的主按钮启动保存，并明确断言保存摘要可见、“查看已保存结果”操作区隐藏。

接续检查在 1600×940、1120×740 两种窗口大小下通过：保存摘要和状态文字显示完整，路线页可以播放和切换三维视图，输入与跨页导航保持锁定，请求关窗后等工程写完再关闭。原生路线与可编辑工程分别完整回读，路线摘要一致，输入方案文件摘要不变。隐藏窗口的 Qt 整窗截图不能合成 VTK 子窗口，三维图像另外从 VTK 渲染缓冲导出到 `viewport-*.png`；已核对模型和黄色路线实际存在。

回归、分层和导入检查的结果见文末“回归结果”。本次补充的窗口检查属于自动化验证，不代表屏幕上的人工操作验收。
