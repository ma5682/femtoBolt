01

选型结论与实施边界

建议首版采用一台 Ubuntu 26.04 LTS x86_64 工业计算机，运行 Qt 6 桌面界面、RGB-D 采集、几何重建、表面覆盖规划和 ROS 2 Lyrical。机械臂保留厂家控制器，底层伺服、受控停止和安全输入由控制器及相应硬件承担。先形成可回放、可校验、可停止的单机产品，再按屏幕形态增加 Windows 或 Android 操作端。

这是一套新产品的目标架构。现有项目已完成的可行性验证可以作为研发输入，但不决定新方案的语言、GUI、操作系统或进程结构。产品范围以人体体表观测、区域编辑、几何路线和机器人协同为中心；首版工程样机的交付与后续医疗用途验证分别立项。

三项直接决策

  1. 计算和机器人集成优先 Linux。 选定 Ubuntu 26.04，而不是笼统写“支持 Linux”。Lyrical 在该平台有 Tier 1 支持，MoveIt、ros2_control、Gazebo Jetty 及 Orbbec ROS 2 驱动有可核查的发行或支持依据。[S02][S07][S08][S15]
  2. 桌面主操作界面优先 Qt 6 Widgets 加 VTK。 首版用 C++20 实现高负载与设备服务；Python 用于算法试验和离线工具。这样可减少 Python 3.14 与现成视觉轮子的耦合，界面仍可独立换成 Windows 客户端。
  3. Android 优先承担触屏终端。 Android 显示预览、编辑工作区、查看计划并提交受控请求；相机、重建和 ROS 放在 Linux 主机。Femto Bolt 未列入本次核查的 Android Wrapper 设备清单，不能据“SDK 支持 Android”就认定这款相机可直接接入。[S05][S06]

何时改选其他组合

如果治疗头或其他关键设备只有 Windows 驱动，采用 Windows 11 设备服务或 GUI 加 Linux 计算及 ROS 主机。若一体机内部可以安装 Linux，而医师希望拿着平板操作，则采用 Android 加 Linux。只有在所有关键供应商均提供经过目标版本验证的 Windows 接口，且能接受独立适配成本时，才考虑全 Windows 主机。

要求完全脱离 Linux、由 Android 同时承担 Femto Bolt 采集、三维重建、ROS 和机械臂集成，会增加相机 ABI、NDK、GPU 算法移植、后台运行、散热和机器人生态等多项工作，不建议作为第一版交付基线。双系统启动只能切换工作环境，不能同时提供一个连续运行的产品。

02

产品需求与使用流程

产品组成按底座、机械臂、工具头、安装在工具头附近的 RGB-D 相机和医师操作屏设计。首版以底座锁定、单台机械臂、单台相机、一次处理一个局部体表范围为默认配置。仰卧与俯卧分别管理采集会话；不假设翻身后旧坐标和路线仍然有效。

需要冻结的产品输入

机械臂品牌型号、工具是否接触人体、有效作用范围、目标空间误差、允许的力与温度等工具限制、机器人控制接口、机身散热空间、预算和交期，进入立项输入表。接触和非接触两类实现都在本方案中给出，具体参数必须来自工具规格、测试和产品风险分析；缺少输入时，相应执行功能保持不可用。

医师的一条完整操作路径

  1. 建立会话并核对身份关联、体位、患者左右和设备状态。人体示意图只负责导航。
  2. 采集当前可见体表的概览，建立有效空间参考，选择右肩等目标部位。系统基于真实观测提出局部扫描范围，由操作者调整。
  3. 采集局部及必要周边；页面显示缺深度、未观察和需要补扫的位置。完成概览不自动赋予局部规划资格。
  4. 检查真实模型，确认可用范围，在绑定本次采集的参考图上涂抹工作区并擦除留空。
  5. 设置经过确认的有效作用宽度、重叠率或行距。查看工作段、贴面换行、分离区域和未完成范围。
  6. 保存版本化计划。接入机器人后，另外进入执行准备，完成当前空间复核、机器人可达性、工具及控制器状态检查。
  7. 台架执行时持续展示运行状态、暂停和停止入口；完成后保存实际轨迹、事件和中断原因。历史回放独立于当前设备画面。

页面设计

建议六个主页面：会话与部位、采集、模型检查、区域标记、路线检查、执行与结果。设备管理、标定、版本和详细诊断放在工程入口。界面显示“需要补扫”“计划已过期”“等待设备”等可行动状态，坐标矩阵和 DDS 参数不进入医师主流程。

返回前一步保留工作上下文。只查看历史不使结果失效；真正改变体位、源模型、标定、区域或工具参数时，系统使相应下游结果过期。补采失败保留上一份完整结果，迟到的后台任务不能覆盖用户新选中的记录。

03

系统分层与设备职责

上位机与下位机描述的是职责，不是固定的操作系统。Linux 工业计算机相对于触屏终端是后端，相对于机械臂控制器仍是上位机。不能因为 Linux 被称为“下位机”，就把它等同于实时伺服控制器。

层主要职责推荐载体典型输出
医师操作层会话、区域、预览、计划确认、运行状态Linux Qt 主屏，可选 Windows 或 Android 屏带版本的用户意图
应用与计算层采集、存储、重建、质量、覆盖与任务状态Ubuntu 26.04 工业计算机模型、报告、审核过的计划
机器人集成层TF、机器人模型、运动规划、状态及厂家适配同一 Linux 主机的独立服务可执行关节轨迹与受控请求
实时设备层插补、伺服、位置或力控制、设备故障处理厂家机器人控制器；必要时独立实时机实际关节状态及设备反馈
独立保护层急停、安全输入、工具输出联锁控制器安全接口及按设计选用的安全硬件硬件许可或停止状态

普通 PLC 或 MCU 可管理灯、按钮、温度、继电器和工具辅助 I/O，但不因使用工业器件就自动具有安全等级。普通 micro-ROS 节点和通用 ROS 通信也不替代独立急停或经过验证的安全功能。[S21]

数据平面与命令平面

原始图像、深度和稠密模型属于大数据通道，尽量留在相机相连的计算主机。设备状态和操作指令属于小消息通道。终端通过应用网关获得缩略预览、显示用模型和任务事件，不直接接收整条高带宽 RGB-D 总线。

机器人控制网、相机 USB 链路和普通用户网络分别设计。需要跨机器共享原始数据时，先计算吞吐并明确拥塞策略，再选择千兆或 2.5GbE 等链路。不能把医院 Wi-Fi 当作有确定时限的伺服通道。

首版进程划分

建议保留五个进程边界：GUI、任务网关及资产索引、采集记录、几何计算、机器人集成。采集服务独占相机，其他模块不能重新抢占设备。重建进程崩溃可独立重启；机器人服务依据自身状态处理停止，不能依赖 GUI 进程是否还活着。

同机使用共享内存或只读资产引用传递大块数据；跨机使用受控文件服务。ROS 消息只携带必要的图像流或描述信息，不把每个点编码进 JSON。进程间接口先定版本，后续替换 GUI 或算法不需要重写控制器接口。

平台支持层级以官方 Lyrical 文档为准。Windows 11 的 Tier 1 主要覆盖 ROS 发行定义的核心范围，不能推导为全部 ROS 包、Gazebo 集成、厂家驱动和算法均有相同支持。Android 的 Linux 内核也不意味着可直接安装 Ubuntu 的 ROS 软件包。[S02]

Linux的具体壁垒

首先是目标发行版。Ubuntu 26.04 的系统 Python 为 3.14 系列，Lyrical 的最低语言要求包含 C++20、C17 和 Python 3.12 至 3.14；Open3D 发布安装页列出的 Python 轮子版本范围未覆盖 3.14，直接把整套算法安装进系统 Python 可能失败。[S02][S18]

解决路径是保持 ROS 运行环境独立，核心几何优先 C++ 构建；需要 Python 算法时，采用单独的已验证 Python 环境或容器，通过数据契约交互。不要替换 Ubuntu 的系统 Python，也不要让不同解释器环境直接共享 rclpy 的二进制扩展。还应验证 GPU 驱动、CUDA、USB 权限、显示服务器和相机固件的具体组合。

Windows的具体壁垒

Windows 原生 GUI、商业设备 SDK 和维护人员经验是优势。壁垒主要在于 Linux 优先发布的 ROS 外围组件、Visual Studio 与 CMake 编译链、DLL 搜索路径、多份 Qt 或 OpenCV 运行库共存、USB 电源管理和自动更新后的再验证。

全 Windows 并非不能实施，但需要为 MoveIt、控制器插件、相机桥接和仿真列出单独的构建与运行清单。若设备只支持 Windows，保留一个 Windows 设备服务，通过版本化协议接入 Linux，比同时迁移整条机器人生态更容易控制范围。普通 Windows 11 与 Windows IoT Enterprise LTSC 的授权和维护周期不同，应按实际 SKU 与采购合同评估。[S27]

Android的具体壁垒

Qt、Flutter、原生 Kotlin 或 WebView 能解决操作界面，却不能自动解决深度相机 SDK、x86 库到 ARM64 的 ABI、USB Host 供电和权限、长时间后台任务以及 GPU 内核移植。Android USB Host 能力需要硬件支持和应用授权，设备掉线后还要恢复权限和连接。[S22]

若相机厂商没有目标型号的 Android 二进制或可编译源代码，这是一项供应商依赖，单靠应用团队无法保证解决。即使能够读到深度流，也还要验证时间戳、内外参、同步、持续吞吐和长时间热稳定性。作为终端时，Android 只承担适量模型显示与输入，风险和研发量显著下降。

WSL 虚拟机与容器

WSL2 适合开发、学习和部分回放。Windows 下把 USB 相机接入 WSL 需要额外的 USB 转发工具和绑定流程，不是默认直通；重连、独占、延迟和图形链路要独立验证。[S20]

容器可以固定用户态依赖，但不能替代主机内核、USB 驱动、GPU 驱动和硬件时钟。Linux 上运行 ROS 容器不等于获得确定性调度；Windows Docker Linux 容器通常仍有虚拟化边界。首版实机控制采用原生 Linux 服务，算法容器仅作为可选隔离手段。

建议锁定的实施栈

GUI与显示： Qt 6 Widgets，VTK 9 系列中与选定 Qt 构建匹配的具体版本，C++20。首版 2D 参考图负责编辑，3D 负责几何检查和路线预览。自由三维标记作为明确的后续需求。

采集与重建： 厂家维护的 Orbbec ROS 2 Wrapper 或原生 SDK 适配器，统一到内部采集契约；OpenCV、Eigen 与 Open3D C++，根据目标算法选择 TSDF 及网格处理。不能让两个进程同时控制相机。

机器人： rclcpp、tf2、URDF/SRDF、MoveIt 2、ros2_control 或厂家提供的等价轨迹接口。优先使用厂家的维护驱动和受控轨迹入口，避免首版自行接管整机伺服。

数据与运维： 完整 RGB-D 与同步信息保存在 MCAP 或明确定义的原始帧容器；SQLite 管理本机索引；模型及报告为外部不可变资产；systemd 管理进程；发行包和容器摘要、配置、固件及标定分别编号。

未通过兼容性门槛时的处理

先判断问题是源代码适配、二进制缺失、驱动限制还是供应商不提供支持。源码问题可在隔离构建环境解决；只有 Windows SDK 的设备可放在 Windows 适配进程；只有 Ubuntu 24.04 或 Jetson BSP 支持的设备可作为独立采集节点。不同 ROS 发行版之间不依赖未经验证的直接通信，必要时通过中立数据契约桥接。

如机械臂厂商只支持 Jazzy，应先要求 Lyrical 支持计划或采用厂家协议适配层。将整个产品改成 Jazzy 加 Ubuntu 24.04 属于显式架构变更，需比较交期与维护成本后再决定，不静默替换用户选定的 Lyrical。

首版推荐的Qt VTK组合

Qt 主线程只处理交互、轻量状态和视图调度；耗时重建、文件写入、模型加载和覆盖计算放在工作线程或独立进程。VTK 的 Qt 原生窗口有明确的 OpenGL 窗口类型与上下文要求，不能把任意 vtkRenderWindow 直接替换进 Qt 控件。[S38]

采用 QML 时，QQuickVTKItem 要处理 Qt Quick 图形后端与 VTK 的线程约束，并按文档在创建窗口前配置所需图形 API。Qt Quick 的平台默认渲染后端不一定与 VTK 的使用方式一致。第一版没有强烈动效需求时，Widgets 可减少这一集成面。[S39]

实时点云、累计点云、最终网格和机器人模型作为独立图层。采集中只更新显示缓冲，不在每帧重新构建整个窗口。点数、面数和纹理尺寸有显示预算；预算调整不能改变用于规划的权威几何。

拾取与区域编辑

第一版优先在绑定真实 RGB 的二维视图涂抹，再利用深度、标定和帧位姿映射到三维。三维视图用于核对边界、缺失、法向和路线；如需自由三维涂抹，必须另外处理背面遮挡、可见性、拾取误差和笔刷面积语义。

降采样点或降面网格要保存回到源几何的索引或重投影依据。鼠标拾取到一个显示三角面，不自动代表它对应的精确源面有效。服务器对最终区域重新验证，历史记录保存模型版本与显示映射版本。

Web和移动端显示

Web 端可以用 Three.js 加 glTF/GLB 预览网格，也可用分块点云。GLB 适合传输渲染资产，但不是自动携带采集血缘、物理单位和质量证明的工程数据包。独立 manifest 记录坐标、缩放、源模型哈希和显示误差。

移动端优先分级加载、降面、纹理压缩和可取消请求。多个终端同时编辑时使用区域版本或乐观锁，后提交的旧版本不得覆盖新版本。显示卡顿可以降低细节，不能降低执行验证条件。

3DGS和SPZ的定位

3D Gaussian Splatting 适合外观呈现和视角回放。它的高斯分布、透明度与渲染质量不自动给出适用于距离、法向、碰撞或接触的真实表面。SPZ 是高斯数据的压缩和交换格式，不是机器人网格或精度证书。[S23][S42]

如需要这类展示，保留一条独立的外观资产分支：记录训练图像、位姿、内参、遮罩、训练配置、模型哈希与轴转换。规划仍依赖经验证的几何表面；外观分支失败不阻断基础几何工作流。采用 gsplat 也不自动覆盖原始 3DGS 代码、模型、训练数据的商业使用许可。[S24][S35]

RGB D采集与三维重建方案

重建目标是得到可追溯、带缺失和质量信息的当前体表。模型应覆盖工作区域及估计法向、边界和避碰所需的周边，而不要求每次都建立完整高精度人体模型。

采集和保存顺序

  1. 读取设备序列号、固件、采集模式、彩色和深度内参、两相机外参及时间戳定义。
  2. 建立或验证参考坐标。移动相机时，为每个被接纳的帧绑定同一时基下的有效位姿。
  3. 将未经过人体或语义 Mask 裁剪的完整场景 RGB-D 写入原始证据层，记录掉帧和拒帧原因。
  4. 生成对齐图像、语义层、选中帧清单、派生点云及质量指标。这些资产可以删除后重算。
  5. 在可靠位姿与质量约束下融合并重建模型。发布模型时同时发布哈希、参数、参考坐标和有效范围。

原始保存可以选择完整连续流，或按清楚的规则保存被选中的原始完整帧；两者应在采集清单中明确。只保存选中帧不能被描述为完整视频证据。Mask 影响派生计算范围，不覆盖原始 RGB-D。

相机安装的三条路线

固定相机： 安装后标定相机与基座或固定参考坐标的变换。机构松动、重新安装、底座变化后重新验证。仅在明确定义两个坐标完全重合且验证成立的特殊场景，才可使用单位变换。

机械臂末端相机： 优先获取厂家控制器的关节或法兰位姿及原始时间信息，通过手眼标定建立法兰到相机关系。相机曝光与机器人状态插值需要同一时间轴。机械臂运动时禁止沿用静态单位外参。

手持相机： 使用可信的外部跟踪或视觉惯性/几何跟踪，配合回环及质量判断。缺少绝对定位时，只能在自己的参考坐标内重建；要交给机器人执行，还需额外建立与机器人基座的可靠关系。人体运动会使静态场景假设失效。

质量输出

每个模型发布观察覆盖、未观察、无效深度、配准残差、法向可信度、边界和冲突区域。质量应能定位到区域或表面单元，而不仅给出“整体良好”的单一分数。跟踪丢失时停止可信融合并保存原因，不能在错误位姿上持续积累看似完整的模型。

对深度精度的验收使用已知几何量具或标定物、多个距离与角度、不同表面反射条件和重复采集。人体或仿体上的最终定位链另行测量。仅比较两次模型相似，不能证明它们都接近真实几何。

手眼关系

TBC(t) = TBF(t) · TFC

T_FC 是相机相对法兰的手眼标定结果。T_BF(t) 使用与图像采集时刻对应的法兰状态，而不是 GUI 接收到图像时的最新状态。

TW0C(t) = TBW0−1 · TBF(t) · TFC

图像像素先按深度单位、内参和畸变模型反投影到 C，再通过 T_W0C(t) 进入固定参考。彩色和深度通常有不同的光学坐标；RGB 上的选区需要使用明确的彩深对齐关系，不能假设同一像素位置代表同一条物理射线。

当已经求得期望工具位姿时，法兰目标由工具标定反算：

TBF* = TBTCP* · TFTCP−1

法向只给出一个方向，不能独立确定完整 TCP 姿态。工具轴定义、绕轴自由度、机器人可达性和碰撞约束将在运动规划中处理。

轴方向与渲染转换

ROS 常用机体坐标为 x 向前、y 向左、z 向上；光学坐标为 x 向右、y 向下、z 向前。具体消息使用的 frame_id 必须与上述定义一致。[S14]

若渲染器明确采用 x 向右、y 向上、视线朝向负 z 的同原点相机坐标，光学坐标到该渲染坐标可使用三轴比例 1、-1、-1。该例仅适用于这一成对定义，不能直接套到机器人基座、Unity 或任意 glTF 场景。左手与右手系转换还要处理三角面绕序、法向和姿态表示。

接口验收使用带颜色的三轴、已知尺寸立方体和若干非对称点，测试正反变换及重投影。几何服务、Open3D、ROS、VTK 和外观渲染之间分别写适配器，明确 API 需要的是 world-to-camera 还是 camera-to-world，避免多次取逆或遗漏取逆。

时间同步

每帧保留设备时间戳、主机接收时间、映射后的单调时间、时间戳含义和同步质量。主机收包时刻不是曝光时刻。机器人状态需保留控制器时间及序号，必要时在可信区间内插值；超出区间或同步误差超限则拒绝用于融合或执行。

多机可评估 PTP、硬件触发或厂家同步方案；NTP 主要适合日志和一般系统时间，不能默认满足相机与末端运动的精度需求。硬件支持、时间戳位置、网络负载和最坏偏差必须一起测量。

etranslation ≈ v · Δt

例如平移速度 20 mm/s、时间误差 10 ms，对应约 0.2 mm 的平移位置误差；这是误差预算示例，未计转动、标定、深度和人体运动。末端相机存在安装臂长时，角速度也会引入随时间误差增长的位置偏差。

标定与误差预算

至少管理相机内参、彩深外参、手眼、TCP、基座与床体关系。标定过程应覆盖实际工作空间和姿态，用不参与拟合的数据独立验证。只报告拟合残差不足以证明全工作空间误差。

误差预算分别包括深度、手眼、TCP、机器人绝对定位、时延、安装形变和患者运动。可以先用保守误差和检查最坏工况；只有独立性等统计假设成立时，才用平方和等统计合成方式。机器人重复定位精度不能替代整条链的绝对定位误差。

患者移动不一定意味着 W0 必须重建，但意味着依赖旧表面的计划需要重新注册、复核或重扫。参考机制本身失效时才重建 W0，并使所有依赖版本失效。

区域从二维到三维

在当前参考图上保存笔画、像素区域和擦除结果，再借助有效深度、标定及该帧位姿映射到模型。缺深度的像素可以保留为待补扫的区域意图，却不能产生被称为可靠的三维点。

区域允许多个分离部分和内部留空。未选择、人工擦除、质量不合格和未观察分别保存；它们的产品意义不同。人体 Pose 或 Mask 只能建议部位和计算范围，不作为最终工作区边界。

行距与覆盖模型

s = w (1 − ρ)

其中有效宽度 w 必须大于零，重叠率 rho 在 0 至 1 之间且不含 1。工具外壳直径用于碰撞，不等于有效作用宽度。有效宽度可能随角度、距离或接触状态变化，需要工具试验提供依据。

上述公式只给出名义行距。曲率、倾角、边界、局部不连续和轨迹执行误差会改变实际覆盖，因此还要在实际曲面上验证覆盖域。平面欧氏圆盘或渲染出的彩色宽带，不能自动作为所有曲面的真实覆盖证明。

工作段 换行段与转场段

工作段 work： 沿可靠目标表面执行覆盖，工具作用状态由独立工具策略决定。

贴面换行 surface_connector： 在同一允许工作表面内连接相邻扫描线。按照产品需求保持贴面，但仍需验证曲率、姿态、速度和接触条件。贴面不自动意味着治疗输出持续开启。

转场段 transfer： 分离工作块之间或需要离开表面的移动，由机器人空间规划单独处理。若产品不允许抬起，应在可行性不足时报告无法形成连续贴面计划，不能擅自跨越留空或缺失。

几何连通性要沿真实邻接表面检查。空间距离很近的两片皮肤、手指或折叠表面不一定连通；不能用最近点短线跨过去。最终插值曲线和工具扫掠体也需检查，不能只检查离散节点。

覆盖结果的表达

分别统计已验证覆盖、明确未覆盖和因数据或计算预算不足而无法判断的范围。目标三维面积无法完整建立时，整体覆盖率标为未知；可报告有依据的已知部分和未解决清单，但不换一个更小的分母宣布完成。

区域、模型、有效宽度、重叠率或工具版本变化后，旧覆盖证据和旧路线失效。规划预算到达上限时保存可诊断的部分结果，状态为未完成；不能把算法正常返回等同于任务完成。

机械臂运动规划与接触控制

机器人链需要把体表几何转化为满足运动学、动力学近似、控制接口和工具约束的实际运动。ROS 2 提供通信与组织方式，MoveIt 提供运动规划工具，ros2_control 提供硬件和控制器接口；三者都不会自动生成针对人体的有效接触策略。

机器人采购和接口门槛

采购前必须取得控制器型号、固件、URDF或CAD、标定参数、负载及惯量范围、TCP配置、关节限位、轨迹接口、状态频率、看门狗、急停及安全输入说明。需要力控制时还要核对六维力传感器、控制模式、可用带宽、数据延迟和故障行为。

供应商声称“支持 ROS 2”仍不够，须写清发行版、CPU架构、Ubuntu版本、驱动版本、支持的控制模式和维护责任。UR 官方 Lyrical 驱动可作为有明确证据的参考；其他品牌需要各自确认，不能类推。[S25]

从表面点到工具位姿

基于表面点、法向、目标间距或接触模型生成 TCP 候选姿态，结合工具轴向定义设置方向。围绕法向的自由度可用于避免关节极限、腕部翻转、线缆缠绕和碰撞。相邻姿态要连续，不能让局部法向噪声造成工具突然转向。

建立全链机器人和环境模型：所有连杆、工具外壳、相机支架、线缆影响、床体及患者空间。目标区允许的工具接触应是局部、明确的例外，不能为方便规划而关闭整个机器人对患者的碰撞检查。

运动规划与时间参数化

用 MoveIt 处理逆运动学、碰撞和自由空间连接；体表工作轨迹仍由产品几何规划提供。连续求解整段路径，检查逆解分支、关节速度、加速度、奇异区和工具姿态约束。笛卡尔插值返回比例不足时，应报告未完成，不执行前一部分后暗示整个任务完成。

为通过检查的关节路径配置速度与加速度边界，并按需求进行 jerk 限制。MoveIt 的时间参数化或平滑可能改变采样和轨迹几何；采用允许几何偏差的方法后，重新检查碰撞和贴面误差。Ruckig 用于 jerk 平滑也不能代替接触控制和安全功能。[S30]

最终输出 trajectory_msgs/JointTrajectory 或厂商等价对象，包含正确关节顺序、位置及时间信息。控制器接口是否还要求速度、加速度、流式更新和时间对齐，以具体厂家协议为准。[S11]

非接触式工具

主要控制工具间距、入射角、空间碰撞和当前人体位置。几何路线生成后仍需检查沿途距离和姿态，人体移动使该约束失效时应中断或重新定位。仅依靠扫描前的静态表面不能保证运行过程中保持间距。

接触式工具

接触涉及组织柔软、压陷、呼吸、滑移、摩擦和工具接触面积变化。按静态 Mesh 匀速走点，不能稳定保证接触力。建议使用厂家支持的力控或专门验证的阻抗/导纳控制模块，结合力传感器、工具结构和设备级限幅。

执行过程至少分为接近、建立接触、稳定贴面、退出接触和转场。每段的接触状态、工具输出状态和失败处理都独立定义。需要外部实时控制时，新增实时计算边界并测量最坏调度延迟；不要让 Python循环、GUI刷新、WebSocket 或普通 ROS 定时器直接闭合确定性力控回路。[S10][S13]

MoveIt Servo 提供在线命令处理及碰撞、奇异性等相关能力，但不是针对具体工具和组织自动调好参数的接触控制器，也不作为独立的安全认证依据。[S31]

停止与恢复

界面“暂停”“停止”、ROS action 取消、厂家受控停止和物理急停具有不同语义。文档、GUI和事件记录分别命名。实际停止行为由控制器和工具设计确认，并测量停止距离、输出关闭延迟及接触状态，不能只看软件返回成功。

暂停恢复要重新核对当前空间、控制器会话、工具、标定和计划哈希。断电、急停或通信中断后不自动续跑；先完成状态核对并重新准备。若暂停期间人体移动，必须使依赖旧表面的计划失效。

正常流程为未开始、采集中、模型待核验、区域已确认、几何计划有效、机器人计划有效、执行准备、运行中和完成。旁路终态包括质量不足、已过期、取消、故障和需要重扫。执行准备是一组前置条件，不是一个可随意点过的页面。

执行许可绑定计划哈希、当前空间版本、标定、工具、机器人配置和控制器启动会话，并有时效。服务端重新检查这些条件；GUI上勾选确认不会覆盖几何失败。版本变化立即使许可失效，迟到的“成功”消息不能重新激活旧许可。

通信可靠性与数据生命周期

通信设计要回答三件事：数据是否新鲜、是否完整、是否来自正确的会话。可靠传输只能解决其中一部分；软件收到确认，也不自动代表硬件动作已经完成。

ROS QoS与网络

预览图像可采用 best effort 和有限队列，以保持新鲜度。用于采集证据的记录链必须检测缺帧、乱序和缓冲区溢出；采用 reliable 也不能消除带宽不足。动态状态设定 deadline、liveliness 或应用层看门狗，静态配置和TF按需要使用可靠且可供晚加入节点读取的配置。[S12]

发布和订阅的 QoS 不匹配会导致看似连上网络却没有数据。使用相同 ROS_DOMAIN_ID 只是通信分组，不是访问控制。首版固定一种 RMW，Lyrical 默认是 rmw_fastrtps_cpp；Fast DDS、Cyclone DDS或Zenoh的切换需要重新验证发现、QoS、大消息与断连恢复，不能当作无成本替换。[S02]

多机部署优先使用固定地址或受控名称解析、明确的网络接口和防火墙规则。需要跨子网时评估发现服务器、路由或网关，不依赖广播恰好能穿过交换机。执行接口限于授权设备与角色；ROS网络不直接暴露到公共网络。

指令的确认与去重

每条请求携带请求ID、幂等键、控制器启动会话、计划哈希、过期时间和预期状态版本。分别记录已接收、已接受、执行中与终态。断线后的重试先查询相同请求的结果，不重新生成一条可能重复执行的动作。

控制器重启后启动会话改变，旧请求失效。事件采用单调序号，客户端掉线后补拉事件并获取当前完整状态。超时不能按“成功”处理；机械动作是否结束以实际状态和厂家反馈为准。

原始与派生资产

建议目录采用 session_id 下的 raw、calibration、derived、models、regions、plans、execution 和 reports。大文件保存在资产仓库，SQLite 保存引用、状态与索引，禁止把数据库文件放在多机器同时写入的网络共享目录。多终端由唯一服务端访问索引；多主机并发业务再评估 PostgreSQL。

保存和恢复事务

新资产先写临时文件，完成后校验大小与哈希，刷新到持久存储，再通过同文件系统内的原子替换发布清单；最后事务更新数据库。跨磁盘操作不依赖原子重命名。数据库索引更新与文件发布之间存在的失败窗口，要通过待提交状态和启动时修复任务处理。

旧模型与旧计划保留，后续重算发布新版本。删除派生层前检查引用；原始证据执行单独保留策略。备份至少包括原始数据、标定、清单、数据库和执行记录，定期在另一目录或机器上验证完整恢复。仅复制数据库不构成完整备份。

隐私与设备维护

使用最小必要的病例关联标识；图像及导出包按角色授权并记录访问。设备本地加密、备份加密、日志脱敏和删除策略进入部署清单。远程维护采用临时授权与审计，不开放未经控制的机器人命令端口。

原始数据带宽示例

假设彩色为 1920×1080 RGB8、深度为 640×576 深度16位，30帧每秒。每帧未压缩数据约 6.96 MB，每秒约 208.74 MB，即 199.07 MiB/s；链路数据率约 1.67 Gbit/s。60秒约 11.66 GiB，尚未计入红外、消息封装、磁盘索引和冗余。

这一例子说明单路未压缩原始流已经可能超过千兆以太网的有效容量。它不代表相机USB线上必然使用此编码或带宽；应按实际输出模式、压缩和对齐行为实测。优先把相机与原始记录放在同一台主机，向终端只传压缩预览和必要资产。

TSDF内存示例

1 m立方区域在2 mm体素下有1.25亿个稠密体素。若仅按每体素16字节估算，约需1.86 GiB；缩小到1 mm时，约需14.90 GiB。真实实现还包括哈希、颜色、索引、临时缓冲和网格内存，不能只按这一最小估算配置设备。

局部重建、稀疏体素、分块与资源上限能降低内存压力。预算不足时返回明确的未完成状态，不静默降低源模型精度后仍沿用原质量结论。

测试体系与验收标准

验收按软件、图形、实机采集、几何计量、机器人台架和具体工具接触分层进行。每份报告记录样本、硬件、版本、参数、测试范围和失败项；不同层的证据不能互相替代。

必须先定义的量化指标

在第一个兼容性阶段冻结空间误差E_req、同步误差D_req、工具姿态或间距要求、允许停止距离、控制器看门狗和接触限制。定义测量方法、参考量具、统计量、最坏工况和通过条件。没有冻结指标时可以完成软件功能开发，但不能把相关执行能力标记为验收通过。

界面性能、存储吞吐和计算资源可以采用前章的初始工程目标。几何精度、接触力和停止阈值须来自产品需求与设备验证，不照抄通用示例。

仿真与真实验证的分工

Gazebo Jetty可验证机器人模型、接口、部分碰撞和任务状态；数字仿真不能证明真实深度相机误差、组织变形或真实接触力。RViz适合工程可视化和调试，也不能因为轨迹动画顺畅就判定实机可执行。[S15][S29]

台架按顺序使用已知几何量具、刚性仿体和可控软材料仿体，先验证空载路径、机器人坐标和停止，再评估工具接触。进入人体相关验证需要单独的产品与验证计划，不由一份软件测试报告直接放行。

需求追踪和完成定义

每个产品需求关联模块、接口、测试编号、报告和版本。一次测试通过只对该组合有效。最终交付必须能从一份执行或规划记录追溯到原始帧、标定、模型、区域、工具参数、机器人配置及应用版本。

异常处理既要验证“成功被阻止”，也要验证用户能理解原因并恢复。例如补扫失败后仍能查看旧模型，控制器断连后可以查看历史，不要求用户删除记录重新开始。

实施启动与交付检查清单

建议从Linux单机方案A启动G0，同时保持GUI网关与机器人适配器的独立边界。这样未来增加Android屏或Windows设备服务时，可以保留原始数据、模型、表面规划和机器人任务契约。

立项时冻结的十项输入

  1. 机械臂品牌、型号、控制器、固件及Lyrical支持责任。
  2. 工具的接触或非接触属性、工作点定义、外壳CAD与有效作用模型。
  3. 相机型号、固件、采集模式、安装位置与USB链路。
  4. 支持部位、体位、可见面以及一次任务的空间范围。
  5. 几何误差、姿态、间距或接触指标的定义与测量方法。
  6. 同步误差、最大运动条件和标定更新条件。
  7. 急停、受控停止、工具输出联锁和通信中断后的策略。
  8. 计算机尺寸、功耗、散热、屏幕形态与网络限制。
  9. 数据保留、导出、权限、备份和远程维护要求。
  10. 工程样机交期、可用团队、硬件与年度维护预算。

前两周的具体交付

完成一张“设备型号 × 操作系统 × CPU架构 × SDK/驱动版本”的真实验证矩阵。每格写可运行、已声明支持但未实测、缺少二进制、源码可编译或供应商未提供支持，避免只填“支持”。

在Ubuntu 26.04上取得一段带完整时间与标定元数据的相机记录；安装Lyrical、MoveIt与所需控制包；读取机器人状态并核对厂家驱动模式；验证Qt和VTK的真实窗口与模型交互；测量一组已知几何的重投影与坐标闭环。

G0结束时输出固定版本清单、阻塞项、采购建议、精度与停止指标、下一阶段排期。如果相机或机器人出现硬阻塞，立即选择对应替代架构，不等GUI完成后再发现底层无法接入。

最终交接包

交付安装包或设备镜像、软件与固件版本清单、许可证和SBOM、配置与schema说明、接口文档、标定流程、示例原始数据、模型及计划、需求到测试的追踪表、实际验收报告、备份恢复与升级回滚说明。每个部署组合只交付经过验证的范围。

验收人员应能在一台干净目标机器上完成安装，使用提供的测试会话回放、重建和规划，并在相应台架验证许可下复现机器人演示。研发人员口头解释和演示录像不能代替这个可重复交接过程。

路线取舍

第一版集中完成可靠的局部体表数据、明确的区域与路线、可验证的机器人接口和故障恢复。全身一次性高精度建模、跨体位自动融合、复杂单指路线、移动底座导航、3DGS外观和多终端并发编辑各自作为后续独立工作包。若底座需自主移动，再引入定位和Nav2；Nav2不能替代表面覆盖或机械臂运动规划。
